# REC-07 durable financial intent receipts

Keyed savings deposits, staff/member withdrawal requests, immediate withdrawals, share purchases/redemptions and loan repayments now use tenant/action-scoped receipts. The payload fingerprint includes authenticated actor, target, exact decimal amount and description (plus withdrawal source/member). The unique claim serializes concurrent retries. A matching completed receipt returns its original response, even if the account or loan subsequently changes; changed details return 409. Receipt completion, money, journal, projection, notification and audit changes share the same tenant transaction. A failed transaction leaves no committed claim; completed receipts are immutable and FORCE RLS-protected. Migration 0045 is append-only; the preceding 44 migrations remain unchanged.

Staff and member API clients persist intent keys in tab session storage before sending supported money forms. Network errors, 5xx, malformed successful responses and refresh retain the key; successful parsed acknowledgement releases it. Changed details cannot silently replace an unresolved intent. Definitive validation/permission/not-found refusal permits correction. Existing step-up retry sends the same keyed body and never automatically retries an uncertain financial response. Explicit caller keys remain unchanged. Front-desk repayment/withdrawal fields now use the existing description contract instead of invalid note fields. The local installer copies the updated member client alongside API/portal, preserves backups/private settings/volumes and migrates without reseeding.

Internal provider (`pay:`) and approved-withdrawal (`withdrawal-request:`) references retain their historical raw journal keys and duplicate-refusal recovery contract. A tenant/reference transaction advisory lock closes their precheck race. They do not receive the new public replay-response semantics; provider matching/allocation workflow atomicity and broader source/payload reconciliation remain separate acceptance work. Loans now lock transition rows to prevent simultaneous duplicate disbursements. Payroll has batch/journal/account lifecycle guards from PR18; its retries still report state conflicts rather than replaying prior HTTP responses.

Fifteen new synthetic PostgreSQL journeys verify response-loss replay, identical concurrency, changed amount/description/target/actor refusal, new identical payments, tenant/action scope, immediate/pending/member withdrawal replay across policy changes, share buy/sell replay, receipt-finalization rollback/retry, insufficient-funds retry, historical/provider keys, immutable receipts and completed-loan repayment/disbursement races. Twelve new staff/member browser transport cases verify key retention and acknowledgement. Local API/DB typecheck/build, 388 API unit cases, 29 browser transport cases and migration/diff checks are required; full draft-PR PostgreSQL and isolated Docker/PowerShell/Chromium checks must pass before handoff.

Compatibility: existing API callers without an idempotency key retain their previous behavior and do not gain arbitrary-request deduplication. Supported browser money forms supply keys automatically; integrations must supply and retain keys for one intended payment. New independent payments need new keys. Cross-tab/device intent coordination, explicit unresolved-intent reconciliation UX, mandatory API keys, response-loss idempotency for other finance routes and full provider/manual-journal workflow acceptance remain open under REC07.
