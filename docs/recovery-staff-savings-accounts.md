# Staff member savings-account opening

An active member could sign in and download an empty savings statement, but staff had no account-opening control on the member page. The API existed. Members without accounts could not complete a normal savings/withdrawal workflow.

The staff member detail page now offers Open savings account for staff with savings.post permission. Staff select an explicit active product (including whether withdrawals are allowed), receive the account number/status, and see its product/balance. Opening never deposits money or reactivates a closed account. Existing money controls are permission-aware, use separate amounts for each account, validate decimal cents within the existing API range, and pass the clicked deposit/withdraw direction directly instead of stale React state. Pending withdrawals are labelled as awaiting approval rather than paid.

Account opening uses the existing server-side natural identity (organization/member/product), member row serialization, and tenant transaction. The server checks product tenant ownership before inserting, refuses new accounts for inactive products and exited members, and returns an existing account without reopening it. Product status changes lock the product before checking usage, coordinating with account opening's shared product lock. No new schema or historical mutation is introduced. Legacy API account opening for non-exited members is retained; the staff UI restricts opening/posting to active members.

The browser's durable financial transport now includes account opening as a natural operation. Original explicit product and verified staff/cooperative scope survive response loss, tabs and browser restart; changed unresolved details and wrong cooperative recovery are refused. Recovery uses the original product and does not invent a new operation. Current account reads are authoritative after recovery. Staff deposits/withdrawals retain the existing keyed posting/recovery protocol.

Regression coverage: PostgreSQL concurrent opening, sequence reuse, zero-money effect, product ownership/inactive refusal, auditor permissions and account/member lifecycle; browser actual product selection, lost committed opening response, competing tab lock, persistent-profile restart/recovery, one account, deposit/withdraw/deposit direction and exact balance, member OTP access, auditor hidden write controls and mobile width; durable-transport and decimal-input tests. Final remote CI/staging evidence is recorded in the recovery backlog after completion; a local installer pass remains a separate acceptance gate.

This slice does not enable production, repair real historical balances, reactivate exited members, discard the user's existing unconfirmed NGN 10000 member request, implement withdrawal reservations/eligibility rules, or complete all member onboarding/product administration. Production remains unchanged.
