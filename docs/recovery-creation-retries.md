# Loan application and manual journal creation retries

Stacked on draft PR #28. Its user local installation acceptance remains pending; the next installer is cumulative. Production remains unchanged.

POST /loans and POST /ledger/journals now require explicit 16–100-character nonblank retry keys, rejecting reserved internal-source prefixes. Old unkeyed callers are intentionally refused. The existing HTTP 201 and response fields remain. A deliberately new key creates a separate application or draft, even with identical details. No content-wide deduplication or reconstruction of historical unkeyed loans is claimed. Historical raw journal keys without receipts and incomplete receipts require reconciliation.

The loans.apply receipt binds actor, member, product, principal, term and original guarantor list within the organization. Loan, guarantor links, application audit and original response commit in one transaction. The response is read through the same transaction, eliminating the earlier post-commit response lookup gap. Identical concurrent retries replay one original response; changed details or actor conflict. Eligibility and later state changes do not regenerate the application or reset status. Existing exact principal/limit arithmetic, two-guarantor rule, eligibility, consent and approval/disbursement behavior remain; this slice does not close the broader consent/policy defects.

The ledger.create receipt binds actor, date, description and ordered canonical line details (account, debit/credit, memo and member association). Draft entry, all lines and original response commit together. Its journal key is derived from organization/action/retry key. Identical retries replay original DRAFT acknowledgement after submission, posting, reversal or period closure; they neither repost nor restore draft status. First creation still validates balanced lines, accounts and an open period. Existing manual-journal arithmetic is retained; wider exact ledger arithmetic and accounting policy remain separate work. Current authentication, grants and browser account-scope checks precede replay. Receipt-finalization faults roll back all creation effects. No migration is introduced.

New loan application and journal draft screens provide member/product/account selections, member search, line editing, confirmation results and current-record lookup. The browser retains original key/payload/scope across uncertain responses, tabs and restart, refuses changed unresolved details and prevents competing tabs from sending another creation. Recovery displays the original created record and allows current-state lookup. Acknowledgement is distinct from current state; same-origin/profile recovery remains the limit. These creation forms do not constitute completed loan or accounting workflows.

PostgreSQL cases cover concurrent identical requests, changed actor/details/guarantors/term/memo/member/account/amount, missing/reserved keys, grants/scope, validation correction, receipt fault rollback, deliberately new keys, tenant/action isolation, incomplete and historical refusal, and later-state replay. Isolated Chromium exercises both real forms, competing tabs, lost committed responses, changed unresolved details, persistent-profile restart, original recovery, observer acknowledgement and current-record lookup. Funding is synthetic fixture data; creation/recovery leave its savings balance and posted journals unchanged. Final-head results and user installation are separate backlog evidence gates.

Remaining: journal submission retry identity, wider exact manual-ledger arithmetic, full loan/guarantor/approval workflows, accounting configuration and registers, historical reconciliation, cross-device discovery and independent financial/provider/production acceptance. PR #28 local acceptance is not inferred from the next-step instruction.
