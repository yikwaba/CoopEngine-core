# Payroll upload preview retry receipts

Stacked on draft PR #27, whose local cumulative installer was accepted on 7 October 2026 at 15:24 Africa/Lagos. Production remains unchanged.

POST /payroll/import/preview now requires an explicit idempotencyKey (16–100 nonblank characters; internal source prefixes remain reserved). This intentionally refuses older unkeyed callers instead of silently creating another batch after a timeout. Existing HTTP 201 and result fields are retained. A new key means a deliberately separate upload, even for identical content. The shared member-import DTO and workflow remain unchanged.

The payroll.preview receipt binds the current actor, exact filename and exact CSV within the organization. Its original batch ID, totals and row errors commit atomically with the PREVIEWED batch. Concurrent identical retries replay one result. Changed actor/filename/CSV conflicts, and incomplete receipts require reconciliation. Parsing/header failures and receipt-finalization failures roll back the receipt and batch together. Current authentication, grants and browser account-scope verification precede replay. Existing preview subscription behavior remains; subscription checks still apply before submission/posting. No new migration, historical batch reconstruction or filename/content-wide deduplication is introduced.

Replay returns the original preview after eligibility changes or later submission, rejection, posting and reversal. It never regenerates rows or resets batch status. Current register status must be refreshed; posting still rechecks eligibility under the existing exact arithmetic and maker-checker controls. Preview and submission do not move money.

The Payroll submissions page accepts a small CSV file or pasted contents, displays validation totals/errors, and lists prepared batches. This bounded slice accepts files up to 16 KB and API CSV strings up to 16,000 characters, within existing JSON limits. It supports existing memberNo/amount savings-only mapping, not arbitrary column mapping or loan/share splits. Zero-valid-row batches cannot be submitted through the page. The browser transport retains the original filename/CSV/key/scope across response loss, tabs and persistent-profile restart; changed unresolved uploads and competing tabs are refused. Recovered validation results appear in the recovery panel. Recovery remains same-origin/profile only and retains the original CSV in that browser until acknowledgement.

PostgreSQL coverage includes concurrent uploads, deliberately new keys, changed details/actor, cross-tenant identity, current guards, missing/reserved/oversized input, validation correction, original errors, changed eligibility, atomic receipt fault rollback, later batch-state replay and incomplete receipts. Isolated Chromium staging covers real file selection, competing tabs, changed unresolved filename refusal, response loss after commit, full restart, original key/CSV/scope and batch/results recovery, observer acknowledgement and mobile width, with one PREVIEWED batch and zero financial effects. Final-head results and local installation are separate backlog evidence gates.
