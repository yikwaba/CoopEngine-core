# REC-10 atomic payroll reversal

The previous payroll reversal committed opposite journals, savings adjustments and batch state in separate transactions. A spent balance or late failure could leave an unreconciled journal correction. It also debited preview rows and guessed the oldest active savings account, including amounts skipped at posting.

Payroll now locks the batch and source-stamped journals, reconciles their per-member savings credits against actual positive DEPOSIT projections, and locks the exact posted savings accounts in ID order. A single tenant transaction creates linked journal corrections, subtracts exact integer-kobo amounts, inserts linked withdrawals, updates batch status and writes both journal and payroll audit records. Every member and journal rolls back together if any part fails. Historical empty journal manifests can resolve by source stamp; inconsistent nonempty links, missing/disagreeing projections, unsupported journal shapes, previously reversed journals, inactive accounts or insufficient funds fail closed. Member exit after posting does not change which account was actually credited.

The ledger reversal helper accepts the existing transaction, locks the original journal and open original period, checks the original is balanced and unreversed, and mirrors SQL NUMERIC debit/credit values and account/member links directly. Generic ledger reversal refuses payroll entries: callers must use the payroll batch endpoint so savings reconcile with the journal. Existing HTTP shapes, payroll.post permission and MFA-sensitive-action protection remain. Original journal lines and posted history are append-only; this change does not repair historical partial reversals or guess missing projections. Closed original periods require an authorized period decision before reversal; no automatic period reopening or current-period adjustment policy is introduced.
