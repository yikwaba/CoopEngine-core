# REC-06 exact payroll preview, allocation and posting

The existing payroll workflow credits CSV deductions to member savings, with one cash debit and per-member savings-liability credits. Loan/share splits, exception mapping and wider payroll policies are not implemented by this slice and remain REC-16 work.

CSV amounts are now parsed as strict decimals into integer kobo, preserving the existing positive 100-million-naira per-row ceiling and rejecting excess scale, exponent/hex notation and non-finite values. New preview rows store fixed two-decimal strings and totals use exact sums. Posting accepts both these strings and historical numeric JSON rows, validates stored amounts, aggregates by member in integer kobo and retains exact values through journal lines, balances and transaction projections. Existing numeric preview/post/detail HTTP contracts are preserved at response boundaries. Audit totals use decimal strings.

Submission and posting lock the batch row through commit. Posting locks active members and savings accounts in consistent ID order before reading/writing balances; these guards prevent concurrent duplicate posting and overwritten ordinary deposits in the tested paths. Existing independent-checker and inactive-member skip rules remain. Preview totals represent the originally eligible CSV rows; the actual posted total is returned and audited separately when a member becomes inactive. Historical rows and balances are not rewritten. Multiple-product account selection, approvals/feature/member policy races and the wider concurrency matrix remain open.

Eleven disposable PostgreSQL API journeys cover exact multi-member previews and journal conservation, strict CSV format/range validation, historical numeric JSON allocation, one-kobo credits to large balances, maximum row inputs, concurrent duplicate approvals/submissions, concurrent ordinary deposits, overflow rollback, checker/closed-period refusal and inactive-member skips. Large opening balances and historical JSON shapes are synthetic fixtures, not reconciled production history.

Payroll reversal balance arithmetic was updated to read either historical numeric or new decimal-string rows exactly, including locked balance subtraction. This does NOT repair reversal transaction boundaries: journal reversal, account movement and batch-state update are still separate transactions, and reversal derives from preview rows rather than actual posted projections. Ledger reversal precision/member links and missing/wrong-product account selection also remain open. REC-10 is a blocker for complete payroll acceptance and should be the next payroll recovery slice; no full reversal completion claim is made.
